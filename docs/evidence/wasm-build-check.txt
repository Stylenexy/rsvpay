2. Remapping those 23 paths to the deploying machine's spelling is not enough on Linux. Symbol names
   carry crate hashes that differ between the two hosts (most likely because proc-macro crates are
   built for the host and feed into their dependents' hashes), e.g.
   near_sdk is Cs64eCvTN3dS3 on chain and Csft7LV3rreZ on Linux. With other names, optimisation keeps
   other functions: 1358 functions on chain, 1369 on Linux; code section 256869 vs 257806 bytes.

3. --remap-path-prefix changes nothing but the path strings: the plain and remapped Linux builds have
   identical function names in identical order and the same code section size.

Conclusion
- No Linux machine, CI runner or Docker image can rebuild 8cKS... byte for byte.
- A Windows build with the MSVC toolchain, rustc 1.99.1 and the same Cargo.lock should match once the
  registry path is respelled: cd scripts && node verify-wasm.mjs. Not yet run on a second Windows machine.
- A deployment anyone can rebuild needs a host-pinned build (cargo near build reproducible-wasm, in
  Docker) and a new keyless account, because rsvpay-v2.testnet has no keys and cannot be redeployed.

verify-wasm.mjs on Linux (same host as above) prints, as designed:
  code hash on chain: 8cKSDEx2G7FqNL5xVspweV5fYC2LWtoeMdKEDngarduw
  this build:         EpNNueE8bYUr1wjvg74LEnELAYKpCtDnUnUPHb1ApdvR
  NO MATCH, as expected on x86_64-unknown-linux-gnu: the deployed build was made on x86_64-pc-windows-msvc ...
  (It respells only the registry prefix, as a Windows build needs. On Linux the rest of each
  path keeps '/', so its hash differs from the per-file remapped build above as well.)
